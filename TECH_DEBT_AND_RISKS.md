## Остаточные риски перед production

### P1 — права VK проверены не полностью

Сервис вызывает `groups.getById` с community token и сверяет группу. Это доказывает доступ token к сообществу, но не является безопасной проверкой права `wall.post`: VK не предоставляет в текущем контракте подтверждённый non-mutating probe для этого community token.

Последствие: канал может пройти подключение и всё равно отказать при публикации. Нельзя проверять право пробной публикацией, пока отдельно не согласованы OAuth/scopes и политика тестовой записи.

Следующий шаг: подтвердить тип VK-авторизации и scopes у провайдера, затем добавить provider-specific проверку без публикации либо явное состояние `verification_required`.

### P1 — защита дублей не закреплена ограничением БД

Сейчас дубли блокируются сервисом под row lock пользователя. Это защищает штатные API-пути, но не защищает прямые административные SQL-операции, будущие worker-пути или ошибочный обход сервиса.

Следующий шаг после согласования схемы: уникальное ограничение для нормализованной пары `(user_id, platform, external_id)` с политикой повторного подключения отключённой записи. Существующие миграции не редактировать; перед новой migration найти и объединить исторические дубли.

### P1 — нет отдельного PostgreSQL race-теста disable-vs-claim

Код содержит блокировку канала и активный predicate в claim, но текущие интеграционные тесты проверяют блокировки пользователя и конкурентные квоты, а не полный interleaving отключения и внешней отправки.

Следующий шаг: fault-injection тест на PostgreSQL с двумя сессиями, барьером между claim и финализацией, проверкой `409` и отсутствия отправки после отключения.

### P1 — exactly-once внешней публикации недостижим

После принятой provider-отправки и ошибки сохранения пост переводится в `unknown`. Платформы VK/TG не дают общего transaction/idempotency key для этого пути.

Последствие: ручная повторная публикация может создать дубль. Автоматический retry intentionally запрещён.

Следующий шаг: показывать пользователю `unknown` с ручным подтверждением, хранить provider request/idempotency metadata там, где платформа это поддерживает, и добавить reconciliation по внешнему ID.

### P1 — старые изображения не имеют отдельной owner-записи

Миграция сохраняет старый `generated_image_key`, а новые изображения получают `generated_assets` с owner-check. Старые посты совместимы с публикацией, но их объектный ключ не связан с `GeneratedAsset`.

Следующий шаг: инвентаризировать legacy keys, создать owner-bound assets только после подтверждения соответствия пользователю и не выполнять автоматический backfill без резервной копии.

### P2 — provider/live-контуры не проверены

Тесты подменяют внешние отправки. VK, Telegram, Yandex Object Storage и Redis production-конфигурация в live не запускались.

Следующий шаг: отдельный staging smoke-test с фиктивными/тестовыми каналами, без публикации в пользовательские сообщества.

### P2 — pre-commit не подтверждён полностью

`ruff check .` и `black --check .` проходят. `pre-commit` содержит hooks, которые могут изменять файлы; запуск в временной Git-копии не смог загрузить hook repositories из-за DNS/network ограничения GitHub.

Следующий шаг: выполнить `pre-commit run -a` в CI или окружении с доступом к pinned revisions и сохранить полный лог.

### P2 — Docker build зависит от внешнего registry

Проверка compose-конфигурации и тестового PostgreSQL прошла, но сборка `python:3.13-slim` ранее не завершилась из-за TLS/network timeout Docker Hub.

Следующий шаг: повторить build в CI; при необходимости использовать корпоративный registry mirror, не меняя версии зависимостей без отдельного решения.

### P2 — неизвестные попытки требуют операционного процесса

Состояния `unknown`, lease expiry и stale worker защищают от слепого повтора, но автоматического reconciliation нет. Без dashboard/alert такие посты могут оставаться в очереди незамеченными.

Следующий шаг: метрики по `unknown`, возрасту lease, provider failures и ручная процедура разрешения исхода.

### P2 — health endpoint проверяет только процесс

`/health` достаточен для порядка старта compose, но не подтверждает доступность БД, Redis или миграционного состояния после запуска.

Следующий шаг: разделить liveness/readiness и добавить безопасные dependency checks без вывода конфигурации.

### P2 — отказоустойчивость Redis в bot client ограничена

Bot API client умеет сообщать недоступность Redis, но операции закрытия Redis-клиента выполняются в `finally` и сами могут выбросить исключение. Это может маскировать исходную ошибку.

Следующий шаг: безопасно подавлять ошибку close после сохранения исходного исключения и добавить тесты отказа Redis.

### P3 — архитектурная граница Celery требует дальнейшего упрощения

Основной publish task принимает ID и вызывает service, но в старых путях остаются sync SQLAlchemy helpers. Это увеличивает риск несовместимого event loop и расхождения транзакционных политик.

Следующий шаг: инвентаризировать все task imports и удалить sync-ветки после отдельного regression-плана.

### P3 — отсутствует единый каталог контрактов provider errors

Ошибки provider частично нормализуются в poster, частично формируются в services/tasks. Это усложняет аналитику и пользовательские сообщения.

Следующий шаг: согласовать внутренние коды `provider_rejected`, `provider_unavailable`, `unknown_outcome`, `asset_unavailable` и отображать их без секретов.

## Проверенные инварианты

- Лимиты каналов сохранены: Free — 1, extended Free — 3, Base/Pro — 999.
- Генерация `text_image` резервирует и фиксирует две единицы расхода.
- Конкурентные квоты и дневной лимит постов проверяются на PostgreSQL агрегатами/row locks.
- Asset download проверяет владельца через JWT и `user_id`; клиентский object key не является авторизацией.
- Callback regenerate использует `callback.from_user.id`.
- Токены каналов шифруются существующим crypto-кодом; `.env` не изменялся и не включается.
- Миграции выполняются до API/worker/beat через compose dependency condition.

## Правила сопровождения

1. Не читать и не коммитить `.env`, реальные токены, логи с provider payload или дампы БД.
2. Не редактировать существующие Alembic migrations; новые изменения схемы обсуждать и выполнять через db-migrate.
3. Для изменений publication state добавлять fault-injection тест на PostgreSQL.
4. Для изменения квот проверять новую сессию и параллельные транзакции.
5. Любой retry после начала provider-вызова считать потенциальным дублем, пока не доказана идемпотентность платформы.
