# Тестовое окружение

Используйте Python 3.13 (как в Dockerfile проекта) и существующий lock-файл:

```bash
POETRY_VIRTUALENVS_IN_PROJECT=true poetry env use python3.13
poetry install --with dev,test --no-interaction
docker compose --env-file /dev/null -f docker-compose.test.yml up -d --wait
poetry run pytest
```

Не запускайте для тестов основной `docker-compose.yml`. Отдельный compose не
использует `.env`, production-сервисы или постоянные volumes. PostgreSQL 16
слушает только `127.0.0.1:55432`; данные находятся в tmpfs. Роль и служебная
БД называются `catruler_test`. В этом одноразовом локальном контейнере включён
`trust`: любой локальный процесс может подключиться без пароля. Конфигурация
не предназначена для production или машины с недоверенными пользователями.

После работы остановите только тестовый стек:

```bash
docker compose --env-file /dev/null -f docker-compose.test.yml down
```

Остановка удаляет временные тестовые данные. Основной стек не затрагивается.

## Выбор проверок

```bash
poetry run pytest tests/unit
poetry run pytest tests/integration
poetry run pytest tests/integration/test_postgres.py
poetry run pytest tests/integration/test_auth.py
poetry run ruff check .
poetry run black .
poetry run pre-commit run -a
```

Unit-тесты не требуют PostgreSQL. Полный набор требует тестовый сервер:
при недоступной БД интеграционные тесты падают, не пропускаются и не
переключаются на SQLite. CI использует такой же PostgreSQL 16 и порт.
Для pre-commit при первом запуске нужен доступ к GitHub/PyPI.

## Изоляция

`tests/environment.py` до импорта приложения отключает dotenv и заменяет
все поля Settings тестовыми значениями. Унаследованные переменные приложения
(в том числе варианты регистра) не используются; bcrypt остаётся настоящим.
Celery использует memory transport, Redis направлен на нерабочий локальный порт,
а ключи внешних провайдеров пусты. Внешние клиенты в соответствующих unit-тестах
нужно подменять явно: bootstrap не является универсальным сетевым sandbox.

Опциональный `TEST_DATABASE_URL` допускается только с драйвером
`postgresql+asyncpg`, loopback-хостом, явным портом, ролью и БД `catruler_test`,
без query-параметров. Не указывайте адрес рабочей БД даже на localhost:
проверка URL ограничивает адрес, но не доказывает принадлежность сервера.
По умолчанию используется отдельный compose на порту 55432.

Fixture `postgres_database` создаёт БД `catruler_test_<uuid>` и удаляет только её
в `finally`. Роль тестового сервера должна иметь CREATEDB. После принудительного
убийства pytest временная БД может остаться до перезапуска тестового контейнера.
Не запускайте остановку контейнера, пока другой тестовый процесс им пользуется.

Fixture `db_engine` применяет существующие Alembic-миграции до head к новой БД.
Она не использует `metadata.create_all()`. `session_maker` создаёт независимые
сессии/соединения для тестов транзакций и конкурентности. Каждая параллельная
операция должна использовать собственную сессию. API dependency переопределена
этой фабрикой и восстанавливается после теста, включая аварийное завершение.

Для отдельного сценария upgrade используйте `postgres_database` и
`await asyncio.to_thread(upgrade_test_database, url, revision)` из
`tests.database`. Runner разрешает миграции только в созданные fixture БД.
Он временно меняет DATABASE_URL для существующего Alembic env: не запускайте
две миграции одновременно в одном процессе. Разные pytest-процессы используют
разные имена БД; pytest-xdist в зависимости не добавлен.

Текущие DB-колонки времени — `timestamp without time zone`, поэтому тестовые
ORM-данные используют naive UTC. Проверку timezone-входов HTTP нельзя заменять
такой нормализацией: это отдельный контракт приложения для следующих задач.

## Границы T01

Проверки транзакций и блокировок подтверждают возможности тестового контура,
а не исправление конкурентных квот приложения. Миграционные тесты проверяют
установку схемы с нуля и upgrade с сохранением существующего пользователя.
Надёжность публикаций, права на каналы и бизнес-транзакции исправляются отдельно.
